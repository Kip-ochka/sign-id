## Набор сквозных сценариев для задачи 09

1. START → SETTING → проверка → ready → CHECK → подпись → task → polling → SIGNING → просмотр → подпись → STATUS SUCCESS.
2. START → SETTING с действительным кэшем: SETTING не появляется; ready может вернуть сразу SIGNING или STATUS.
3. CHECK/SIGNING без сертификатов, с несколькими, с извлечённым токеном после выбора; ошибка CryptoPro и BACK без повторной подписи.
4. Подпись создана, отправка получает временную ошибку: повторяется только отправка; длительный timeout не доказывает, что сервер не обработал запрос (Q-12).
5. Последовательные SIGNING для разных групп документов; optional step отсутствует; фильтры и документы обновлены.
6. 401 при state/poll/document; одновременно приходит старый ответ — он не возвращает старую session/экран.
7. Ошибка справочника и ErrorBoundary; fallback работоспособен; BACK не зацикливается на STATUS.
8. Локальный HTTP-сервер получает полный комплект синтетических данных MVP `single/other/detached` для одного и нескольких документов. При сбое на втором из трёх документов третий не подписывается и отправки нет. Остальные режимы дают локальный fallback. Проверить таймер STATUS с BACK и URL и сохранение session/token между процессами.

## Уровни доказательств

- Unit: обновление состояния процесса, кэш/TTL, алгоритм выбора хэша, фильтры, маппинг ошибок, таймеры с подставными часами.
- API/интеграционные с синтетическими данными: multipart, реальный локальный HTTP там, где это уже используется; сохранение имеющихся Jest-тестов.
- UI: состояния и сценарии взаимодействия, визуальная проверка; существующая конфигурация Jest Node сама их не покрывает.
- Браузер с локальным HTTP-бэкендом: HTTP 303, рестарт при 401 и доступ к X-Request-Id.

В отчёте указать результаты моков, локального HTTP и браузера. Доступ к интеграционному стенду в рамках задач SIGNING не предусмотрен. Поведение интеграционного бэкенда остаётся неподтверждённым.
