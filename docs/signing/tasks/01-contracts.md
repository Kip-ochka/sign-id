Статус: завершена. AC-22 проверен в Chrome с локальным HTTP-бэкендом. Проверка интеграционного бэкенда относится к задаче 09. Результаты в [PROGRESS.md](../PROGRESS.md).

## Вход

[Контекст](../PROJECT_CONTEXT.md), [API](../API_CONTRACT.md), [CryptoPro](../CRYPTO_CONTRACT.md), [решения](../DECISIONS.md); `src/shared/api`, `src/shared/hooks/useInquiryId.ts`, `ERRORS_REFERENCE.md`, `API_TESTING.md`.

## Работа

1. Сверить актуальные схемы/экспорты/тесты с постановкой. Зафиксировать исходные результаты `npm test`, typecheck, lint; существующие ошибки отделить от новых.
2. Исправить подтверждённое расхождение: optional `screen.step`. Для остальных расхождений использовать таблицу API, а не менять схемы по догадке.
3. Применить Q-01/Q-03 и клиентскую часть Q-04 в моделях и фикстурах. Открытые серверные и криптографические контракты перечислены в DECISIONS.md. Готовить независимые модели по мере сверки.
4. Подготовить синтетические примеры каждого process, task, настроек, fallback, фильтров без вложенных полей и разных кнопок. Не копировать примеры исходника с комментариями и лишними запятыми как валидный JSON.
5. Разделить сырой ответ, валидный process DTO и локальное UI-состояние. Определить точку однократной runtime-валидации; ошибка схемы не должна приводить к частичному отображению.
6. Сохранить сериализацию multipart и регрессионные проверки. Явно описать изменения транспорта, необходимые для abort/timeout/status/headers; `getDocument` уже возвращает DocumentData.
7. Проверить HTTP 303 от тестового бэкенда в браузере. Если сценарий недоступен, записать блокер и воспроизводимый план проверки.

Для AC-29 проверить, что Zod сохраняет `SETTING.session` и `SIGNING.token` при разборе ответов state и pollStatus. Оба поля уже есть в схемах. Добавить поля в API только при обнаружении фактической потери при разборе. Для MVP подготовить валидную фикстуру single без архивных хэшей, фикстуру SIGNING с несколькими документами, а также отдельные фикстуры batch/archived/XML/attached. Не отклонять неподдерживаемый режим общей ошибкой DTO раньше проверки режима, если из ответа можно определить его параметры. Он должен давать локальный fallback R-27. Проверить сохранение числового `STATUS.timer`.

## Не входит

Реализация экранов, подписи и очистка криптослоя. Установка новых библиотек без конкретной потребности. Предположительный session/token протокол.

## Приёмка

- AC-04/AC-14/AC-15 покрыты на уровне моделей/сериализации; AC-22 имеет фактический результат или явно незакрытый блокер.
- Фикстуры валидны, минимум один отрицательный пример на критичное расхождение.
- Ни одно нерешённое Q-* не скрыто в обязательном поле, magic constant или приведении типов.
- Typecheck и затронутые API-тесты проходят; новая схема не ломает подтверждённые multipart-сценарии.
