# Нормализованные требования

R-* — требования из запроса и исходника. D-* и Q-* определены в [DECISIONS.md](DECISIONS.md). API и криптографические детали вынесены в отдельные спецификации.

## Границы

**R-01.** Создать клиентский процесс подписания для банковских систем. Вход — ссылка из SMS с `?id=<inquiry_id>`. Отправка SMS, выпуск сертификата, реализация бэкенда не входят в объём.

**R-02.** Навигация только через состояние приложения, без React Router. Все стили компонентов — CSS Modules. Создать простой интерфейс по [UI_SPEC.md](UI_SPEC.md); готового дизайна нет.

**R-03.** Криптослой примера переработать и очистить; оставить только используемые операции. Предпочитать библиотеку `crypto-pro-actual-cades-plugin`, при необходимости её `execute`.

## START и общий процесс

**R-04.** Получить `inquiry_id` из единственного непустого query `id` и хранить отдельно от session/token. При отсутствии, пустом, пробельном или повторном параметре показать локальный STATUS «Ссылка недействительна» без API-вызовов. Убрать чтение и запись `digitalid_sign_inq` (Q-03).

**R-05.** Сначала `getSettings('settings')`. При HTTP не 200, ошибке сети или невалидной схеме использовать целиком defaults: `retry_time=1000`, `retry_addition=200`, `retry_count=3`, `pull_time=10000` (времена в мс). Сохранить выбранные настройки в React Context. Ошибка настроек не останавливает старт.

**R-06.** После настроек вызвать `state('start')`. Проверить фактический ответ по схеме, сохранить валидный результат в Context. Ответ с `process` определяет следующий процесс; `{task}` запускает polling. Событие запроса не определяет заранее следующий экран.

**R-07.** Обрабатывать общие HTTP-ошибки по матрице в `API_CONTRACT.md`. Для 429/504/timeout бюджет операции равен `max(1, retry_count)` с учётом первого запроса. Задержка `retry_time + randomInteger(1, retry_addition)`, при нулевой добавке только `retry_time` (Q-01). Не повторять криптографическую операцию из-за сетевого retry.

**R-08.** При первом 401 от REST.01–03 остановить текущие операции, очистить `session` и `token` и один раз перезапустить START. Повторный 401 от этих операций ведёт в STATUS `RESPONSE_ERROR`. Новая заявка или явный повтор сбрасывают лимит. Поле `SETTING.session` сохраняется в localStorage на 115 минут; новая сессия заменяет прежнюю с новым сроком. Действующая сессия используется после перезагрузки и смены заявки. Каждый запрос, включая retry, передаёт актуальную `session` в `Session-id`; при её отсутствии/истечении заголовок не отправляется. Истёкшая запись удаляется. После 401 от любого API-запроса заголовок опускается до получения валидного SETTING или смены заявки. `SIGNING.token` хранится только в памяти (Context) и передаётся заголовком `X-integrity-token` в `/document` и `/state/signing`, включая retry.

## SETTING

**R-09.** При получении `process=SETTING` сначала проверить кэш успешной настройки, **до отображения SETTING**. Если кэш действителен, оставить предыдущий экран и вызвать `state('ready')`. Это правило действует после любого процесса, не только START.

**R-10.** Кэш — localStorage `digital_id_sign`. Запись содержит `inquiry_id`, время успешной настройки, `navigator.userAgent` в поле `device` по Q-05 и пройденные этапы. Кэш действителен при совпадении заявки и строки userAgent, возрасте меньше 24 часов и наличии успешного результата всех трёх обязательных проверок. Смена браузерного профиля без записи или изменение userAgent требует новой проверки SETTING. Идентификатор заявки берётся из ссылки. Битая или недоступная запись даёт промах.

**R-11.** Если кэш не подходит, показать SETTING. По кнопке «Запустить проверку» выполнить обязательные этапы по одному разу в порядке `extension → program → certificate`. `extension` проверяет браузерное расширение и доступность cades plugin API. `program` проверяет CSP 5.0 и выше независимо от номера сборки. `certificate` ищет действующие сертификаты с привязкой к закрытому ключу без серверных фильтров SETTING.

**R-12.** `screen.lists.testing` задаёт строки SETTING, их порядок, тексты, описания и подписи кнопок. Список может отсутствовать или быть пустым. Клиент привязывает локальные статусы `WAIT`, `RUNNING`, `SUCCESS` или `ERROR` к отображаемым строкам по имени.

**R-13.** Ошибка останавливает последовательность. Если серверная строка этапа есть, SETTING показывает в ней ошибку и кнопку «Подробнее». Если строки нет, клиент сразу открывает STATUS по ключу ошибки CryptoPro. Отсутствие сертификатов даёт `NO_CERT`. После успеха всех трёх этапов сохранить кэш и сертификаты в памяти и вызвать `state('ready')`.

## CHECK

**R-14.** При входе заново выполнить проверку окружения/поиск сертификатов с фильтрами текущего ответа, даже если SETTING был пропущен по кэшу. В выборку входят все уникальные совпадения, действующие на момент проверки. При ошибке перейти в STATUS. При пустой выборке — `NO_CERT`.

**R-15.** Один сертификат используется автоматически; при нескольких пользователь выбирает. Вариант содержит ФИО (`title`) и организацию (`description`). До выбора нескольких сертификатов подписание недоступно (D-05).

**R-16.** Показать `screen.consent.text`, выделить `hypertext` как ссылку `url`. Исходник задаёт согласие нажатием кнопки, отдельный обязательный checkbox не требуется.

**R-17.** Только по действию пользователя подписать тестовый хэш из `screen.test_document`, выбрав алгоритм сертификата, формат и позицию из ответа. CHECK использует тот же набор параметров MVP, что R-20. Передать результат через `state('check')`: тестовый документ, метаданные подписавшего сертификата, файлы подписи и сертификата. Данные человека/организации/издателя извлекать из фактически использованного сертификата.

## SIGNING и документы

**R-18.** При входе повторить поиск по текущим фильтрам и отобразить `screen.title/message`, необязательный `screen.step`, список `screen.lists.documents`, выбор сертификата и кнопки. Не вычислять число шагов самостоятельно.

**R-19.** По действию у документа вызвать REST.03 с его id, проверить ответ, отобразить средствами браузера, если формат поддерживается, иначе скачать. `format` содержит расширение без начальной точки в произвольном регистре, MIME файла определяется по расширению. Ошибка документа обрабатывается отдельно от ошибки REST.01. Ответ REST.03 использует multipart.

**R-20.** MVP поддерживает `single/other/detached` с профилем `CADESCOM_PKCS7_TYPE` без клиентского штампа времени. Для SIGNING выбрать один сертификат, определить его алгоритм, затем последовательно вызвать одну и ту же операцию для хэша каждого документа. Для N документов получить N отдельных подписей. CHECK подписывает один тестовый документ. Неподдерживаемый режим, включая `batch`, `archived`, `xml` и `attached`, ведёт в локальный fallback R-27 до вызова подписи.

**R-21.** После создания всех подписей один раз отправить `state('signing')` со всеми документами, метаданными выбранного сертификата и отдельным файлом `<document.id>.sig` для каждого документа. При ошибке отдельной подписи остановить цикл и обработать ошибку. Частичный комплект не отправлять. Следующий ответ может снова быть SIGNING, другим процессом или task. Не считать успех CryptoPro подтверждением завершения серверного процесса.

## Polling

**R-22.** REST.01 с 303 и `{task}` запускает ожидание; REST.02 с 200 и `{task}` продолжает его. В описании START также допустим task при 200 — поддержать единый валидный task-ответ (D-02), фактический браузерный 303 проверить отдельно.

**R-23.** Выждать `pull_time` до первого poll; пока сервер возвращает task, продолжать с этим интервалом. Показать экран ожидания. При process остановить polling и обработать процесс, включая предварительную проверку кэша SETTING. Сетевая ошибка poll использует общую матрицу retry.

## STATUS и ошибки

**R-24.** STATUS поддерживает SUCCESS, WARNING, ERROR и отображает title/message, accent и необязательную secondary. Для готового серверного экрана сохранять level. Локальные экраны справочника имеют уровень WARNING. Только на SUCCESS по истечении `timer` выполнить распознанное действие `accent` один раз по правилам Q-10. На WARNING и ERROR действие запускается вручную.

**R-25.** Кнопка STATUS с `url` выполняет внешний переход по полному HTTP(S)-адресу следующего процесса. `process=BACK` возвращает к предыдущему рабочему экрану из состояния приложения. Поля `action`, неизвестные process и сочетание url/process — Q-11.

**R-26.** Известную локальную ошибку сопоставить с ключом справочника и получить экран через `getSettings(key)`. При ошибке/невалидном ответе справочника использовать локальный fallback. Для неизвестной ошибки или ключа `null` сразу fallback без сетевого запроса. Это же правило применяется к JS/TS-ошибке, перехваченной ErrorBoundary; не выполнять рекурсивную загрузку экрана ошибки.

**R-27.** Локальный fallback: STATUS/WARNING, title «Что-то пошло не так», message «Пожалуйста, попробуйте повторить попытку позже», accent «Попробовать снова» с `process=BACK`.

**R-28.** Читать `X-Request-Id` из REST.01/REST.02 для отображения на статусе ошибки. Не заменять идентификатор исходной операции идентификатором последующего getSettings. Отсутствующий заголовок не должен ломать экран.

## Требования к целостности выполнения (D-03)

Одна активная команда подписи; повторные клики не создают дубликаты. Таймеры и результаты старой заявки/операции не меняют новый экран. На смене заявки, рестарте и unmount отменять запросы, где возможно, и игнорировать устаревшие результаты. Успешный HTTP retry использует уже созданную подпись. Возврат с STATUS сам по себе не подтверждает новое подписание.

Это инженерные дополнения для однозначной реализации R-07/R-08/R-25, а не дополнительные серверные гарантии идемпотентности.
