# Контекст проекта SIGNING

## Текущее состояние на 18.11.2026

- `src/main.tsx` монтирует `App` без пропса inquiryId. `App.tsx` однократно считывает id из ссылки при монтировании и выбирает страницу по процессу из Context. `ProcessProvider` в `widgets/signing-process` создаёт новое состояние при смене id. Компактный `useProcess.ts` хранит данные текущего запуска и собирает независимые фичи из `process`.
- `SETTING.session` сохраняется в localStorage на 115 минут, восстанавливается при загрузке и используется в `Session-id` до истечения/401. `SIGNING.token` хранится в памяти и передаётся в `X-integrity-token` для document/signing.
- SETTING проверяет браузерное расширение, CSP и наличие действующих сертификатов и использует кэш полного набора проверок на 24 часа. CHECK и SIGNING выполняют актуальный поиск сертификатов по своим фильтрам. SIGNING получает документы через REST.03, создаёт object URL для просмотра или скачивания и освобождает URL при закрытии или смене экрана.
- Рабочий адаптер в `src/shared/services/cryptoPro/` проверяет Browser Plug-in и CSP, отбирает сертификаты и создаёт подписи. Production собирается из `index.html`.
- Порядок запуска описан в [README проекта](../../README.md). Результаты локальных прогонов и граница стендовой приёмки приведены в [PROGRESS.md](PROGRESS.md).
- `npm run dev` запускает Vite. Dev и сборка используют одну точку входа и реальный адаптер КриптоПро. В dev `/proxy/services` проксируется на локальный Express-мок (`npm run mock`, порт 3001 или `MOCK_PORT`). Ответы и ручной выбор процессов — в корневом `mock-data.mjs`; автоматической смены ответов нет. Production использует относительные маршруты API на том же origin.

## Что можно переиспользовать после сверки

- `requests.ts`: маршруты и типизированные события; `helpers/files.ts`: разделение JSON, подписей и сертификатов.
- `helpers/parseDocumentResponse.ts`: разбор multipart; сейчас проверяются метаданные, но не весь `documentDataSchema`.
- `errorsBase.ts`: фактические ключи справочника; не переносить старые коды `ER0202/ER0204` как новый продуктовый контракт.
- Отдельные операции CryptoPro, если их поведение соответствует `CRYPTO_CONTRACT.md` и подтверждено тестом.

## Почему криптослой требует замены

`sign-document/SignDocument.ts` выбирает сертификат, запускает подписи через `Promise.all`, использует `createDetachedSignature` без явного выбора алгоритма и нормализует Base64 удалением символов. Этот подход не покрывает параметры нового процесса и может скрыть некорректные данные. Не переносить его целиком.

`check-workplace/useCryptoProWorkstation.tsx` проверяет extension/plugin/CSP, но не реализует весь новый трёхэтапный сценарий с фильтрами сертификатов и кэшем. В нём также смешаны проверка и UI (`CryptoErrorAlert`).

`generate-request/`, `install-certificate/`, их `cades_api`, утилиты контейнеров и `style.less` — кандидаты на удаление в задаче 04, если поиск подтвердит отсутствие потребителей в новом процессе. Выпуск/установка сертификатов не входят в заданный функционал. Ссылки на инструкции по установке допустимы.

## Архитектура после FSD-рефакторинга от 18.11.2026

Имена слоёв согласованы с пользователем: `process` соответствует features, `screens` — pages. Направление зависимостей: `App/app → screens → widgets → process → entities → shared`. Подробности и контракты подключения будущего UI: [ARCHITECTURE.md](ARCHITECTURE.md).

- `widgets/signing-process/useProcess.ts` хранит состояние в React и собирает сценарии. Отдельные модули отвечают за операции/401, применение ответов, срок сессии и композицию подготовки подписей. Context и навигация находятся в том же widget.
- Фичи в `process`: START; SETTING с проверкой и кэшем; подготовка CHECK/SIGNING; общий цикл подписи и отправки; документы; STATUS/ошибки; polling. Фичи не импортируют страницы, widgets или соседние фичи.
- `entities/signing` содержит модель заявки, переходы состояния, хранилище сессии, сетевые операции и используемые несколькими сценариями компоненты сертификата/кнопок.
- `shared/api/network.ts` содержит retry и чтение request id; `shared/lib` — таймеры, URL и resolver криптоошибок; `shared/ui` — общий каркас и загрузку. Адаптер CryptoPro остаётся в `shared/services/cryptoPro`.
- Страницы `screens` подключают Context и компонуют widgets/features. Существующая разметка и CSS перенесены без изменения дизайна. Текущий UI временный; будущему интерфейсу доступны данные и команды Context без зависимости сценариев от разметки.
- Импорты между срезами проходят через публичные `index.ts`. ESLint проверяет направление слоёв, изоляцию соседних срезов и публичные API. Интеграционные тесты могут собирать несколько слоёв.

## Команды и ограничения проверки

В `package.json` есть `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, `npm run format:check`. Jest запускает `*.test.ts` в Node. Сценарные тесты в `src/widgets/signing-process/process.test.ts` используют React Test Renderer и подставной сетевой адаптер. Композиция страниц и фичей проверяется в `src/app/processComposition.test.ts`; правило FSD — командой `node --test test/fsd.test.mjs`. Не объявлять готовность UI на основании только API-тестов.

`API_REFACTOR_BRIEF.md` — историческая постановка, а не текущая задача. `API_TESTING.md` описывает существующие тесты; информацию о версиях и совместимости при изменении зависимостей проверять заново. Серверные контракты и установленный CryptoPro в ходе этого анализа не проверялись.
