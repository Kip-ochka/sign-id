# API: целевой сценарий и текущий транспорт

Читать вместе с [REQUIREMENTS.md](REQUIREMENTS.md) и [DECISIONS.md](DECISIONS.md). Маршруты и формы файлов ниже установлены по существующему `src/shared/api/`; это исходная база, а не замена отсутствующей серверной спецификации.

## Операции

Пути `/proxy/services/...` принадлежат API бэкенда. Префикс маршрутов подписания: `/proxy/services/corp-digital-id-sign/api/public/v1`.

| Обозначение | Функция / HTTP                                                                                            | Тело                                              | Текущий результат функции                  |
| ----------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------ |
| Настройки   | `getSettings(key)`, GET `/proxy/services/sbercraft-dict-ext/serviceProperties/corp-digital-id-sign/{key}` | Нет                                               | AxiosResponse; `settings` или экран ошибки |
| REST.01     | `state(event, body, files?)`, POST `/state/{event}`                                                       | JSON для start/ready; multipart для check/signing | AxiosResponse с process/task               |
| REST.02     | `pollStatus(body)`, POST `/poll/status`                                                                   | Общие поля + task                                 | AxiosResponse с process/task               |
| REST.03     | `getDocument(body)`, POST `/document`                                                                     | Общие поля + document_id                          | Разобранный DocumentData                   |

Общие поля: `inquiry_id`, `req_time` (ISO datetime с часовым поясом), `sc_name='urn:front-corp-digital-id-microfront'`, `sp_name='urn:corp-digital-id'`. Формирование времени при retry и идентичность повторного запроса зависят от Q-12.

Значения событий HTTP: `start`, `ready`, `check`, `signing`. Процессы ответов: `SETTING`, `CHECK`, `SIGNING`, `STATUS`. `START` и предлагаемый `WAITING` — локальные состояния интерфейса, не новые значения серверного контракта. Любое событие может вернуть любой поддержанный процесс.

Схема SETTING принимает строковый `session`, схема SIGNING принимает строковый `token`. Тесты с локальным HTTP-сервером подтвердили сохранение обоих полей после Zod-валидации тел `state` и `pollStatus`. В задаче 02 Context должен хранить последние валидные значения текущего запуска и очищать оба при 401 и смене заявки. Запросы MVP сохраняют текущую форму.

## Граница валидации

- `state` и `pollStatus` возвращают `AxiosResponse<unknown>`. После проверки HTTP-статуса сценарий вызывает `parseProcessResult(response.data)` один раз на ответ. Для настроек и справочника аналогичная точка входа использует `settingsResponseSchema.safeParse` и `screenResponseSchema.safeParse`.
- Успешный разбор даёт `kind: 'process'` с полным `ProcessResponse`, `kind: 'task'` с `TaskResponse` или `kind: 'unsupported-mode'` с тройкой параметров и локальным fallback R-27. При наличии одновременно `process` и `task`, пустом или пробельном `task`, неизвестном процессе и ошибке схемы поддержанного процесса результат содержит ошибку валидации. Сценарий направляет её в `RESPONSE_ERROR` без применения частей ответа.
- Для CHECK и SIGNING явный неподдерживаемый режим определяется по трём строковым полям до проверки экрана и параметров подписи. Архивные хэши опциональны на уровне DTO и проверяются на формат при наличии. Для поддержанного режима сохраняется текущая схема остальных полей. Q-14 определяет обязательность полей для будущих режимов и отсутствующие реквизиты сертификатов.
- Сценарий задачи 02 строит локальное состояние из результата разбора. `process` заменяет DTO экрана целиком, включая список документов. `task` переводит в локальный WAITING. `unsupported-mode` переводит в локальный STATUS/WARNING без подписи и запросов. START, счётчики попыток и 401, история BACK и `STATUS.timer` как запланированное действие на SUCCESS относятся к локальному состоянию. Числовой `timer`, включая ноль, сохраняется в валидном STATUS DTO.
- `stateResponseSchema` и `pollStatusResponseSchema` остаются схемами полного DTO task/process. В сценарии используется `parseProcessResult`, который также умеет распознавать неподдерживаемый режим при неполном экране.

## Настройки и их валидация

| Поле           | Default | Назначение                                     |
| -------------- | ------- | ---------------------------------------------- |
| retry_time     | 1000    | База задержки retry, мс                        |
| retry_addition | 200     | Верхняя граница случайной добавки, мс          |
| retry_count    | 3       | Максимум HTTP-попыток с учётом первого запроса |
| pull_time      | 10000   | Пауза polling, мс                              |

Все четыре значения проверять вместе; ошибка одного поля означает полный fallback. Схемы сейчас допускают неотрицательные целые, включая ноль. При `retry_addition=0` пауза равна `retry_time`. `pull_time=0` остаётся в Q-13. Не менять имя `pull_time` на `poll_time` в DTO.

## Multipart check/signing

Порядок частей: `request`, затем повторяющиеся `signatures`, затем повторяющиеся `certificates`.

- `request`: JSON, MIME `application/json`; check содержит `test_document`, signing — `documents`; оба содержат массив метаданных `certificates`.
- Метаданные: `type='signed'`, `serial_number`, `thumbprint`, `expires_at`, person/organization/issuer. Брать из выбранного сертификата, не из фильтров.
- Подпись: декодированные Base64-байты, `application/pkcs7-signature`. CHECK — `test.sig`; документная SIGNING — `<document.id>.sig`. CHECK отправляет одну отсоединённую подпись, SIGNING отправляет N отдельных подписей для N документов.
- Сертификат: Base64-текст без PEM-заголовков, `<serial_number>.b64`, `text/plain`.
- В JSON отсутствуют подписи и `certificate_base64`. Текущий `createStateFormData` удаляет эти файловые поля; сохранить защиту и проверки содержимого.
- Не задавать multipart boundary вручную. Не исправлять произвольно повреждённый Base64 удалением символов.

В `single` для N документов собрать N отдельных `signatures` и передать их одним `state('signing')` после полного успеха. `documents` и файлы подписи связаны через id, сертификат выбран один на весь список. При разрешённом сетевом retry повторно использовать весь готовый комплект по Q-12.

## Ответ документа

HTTP-запрос использует `responseType: 'arraybuffer'`. Тело — `multipart/mixed` с boundary. Часть `response`: JSON `{document_id,title,format}`. Часть `file`: текст Base64 содержимого. Текущий результат `getDocument`: `{document_id,title,format,base64}`.

Нужны проверки частей, JSON, метаданных, декодирования содержимого и соответствия document_id запрошенному документу (последнее — D-03). Не считать `getDocument` функцией, возвращающей AxiosResponse; успешные headers сейчас наружу не выходят. HTTP-ошибки Axios и ошибки парсинга различать на сценарном уровне. Не заменять multipart-ответ ожиданием JSON с полем `file`.

## Единая матрица ошибок

| Результат                                 | REST.01 / REST.02                                            | REST.03                                           |
| ----------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------- |
| 200 и корректное тело                     | Обработать process/task                                      | Просмотр/скачивание                               |
| Невалидное тело                           | RESPONSE_ERROR                                               | RESPONSE_DOC_DOWNLOAD_ERROR                       |
| 503                                       | SERVICE_UNAVAL                                               | SERVICE_UNAVAL                                    |
| 401                                       | Первый → START без старой сессии, повторный → RESPONSE_ERROR | То же                                             |
| 403                                       | SERVICE_UNAVAL                                               | RESPONSE_DOC_DOWNLOAD_ERROR                       |
| 400, 500                                  | RESPONSE_ERROR                                               | RESPONSE_DOC_DOWNLOAD_ERROR                       |
| 429, 504, timeout                         | Retry; при исчерпании RESPONSE_ERROR                         | Retry; при исчерпании RESPONSE_DOC_DOWNLOAD_ERROR |
| Отмена устаревшей операции                | Игнорировать результат, без STATUS (D-03)                    | То же                                             |
| Прочий статус / network error без статуса | В исходнике не определён; D-06/Q-13                          | В исходнике не определён; D-06/Q-13               |

Для `getSettings('settings')` всегда правила R-05, а не эта таблица. Для `getSettings(errorKey)` всегда локальный fallback при неуспехе; его 401 не должен запускать рекурсивный рестарт. Для 303 REST.01 нужен отдельный разбор task, а не общее «не 200 → ошибка».

До решения Q-12 для check/signing применяются повторы при HTTP 429/504 с прежними данными и `req_time`. Локальный таймаут отправки завершает операцию с `RESPONSE_ERROR`. Длительность клиентского таймаута остаётся открытой в Q-13.

Известные ключи ошибок определять через `errorsBase`, при подписании сначала `signingErrorOverrides`. Например, `0x80004005`: создание объекта → E_FAIL, подписание → SIGN_FAILED. Записи `null` и неизвестные значения не превращать в произвольный getSettings. Название `SERVICE_UNAVAL` сохраняется буквально.

## Polling и retry

Одна операция получает `max(1, retry_count)` HTTP-вызовов, включая первый. Модель `getHttpAttemptLimit` принимает валидный DTO настроек. Каждый следующий обычный poll получает новый бюджет. Перерисовка и retry текущий бюджет не сбрасывают. Для отправки подписи дополнительно применяется Q-12.

Модель `getUnauthorizedAction` выбирает START при первом 401 и `RESPONSE_ERROR` при повторном. Сценарий хранит факт использованного рестарта весь запуск, в том числе после успешного ответа, и сбрасывает его при новой заявке или явном повторе пользователя.

1. Принять валидный task, показать WAITING, сохранить текущий task и контекст возврата.
2. Выждать `pull_time`, выполнить один poll.
3. Ответ task: обновить task из ответа и запланировать следующую паузу. Ответ process: завершить цикл, передать в общий обработчик процесса.
4. При временной ошибке выполнить retry этой сетевой операции; параллельный обычный poll не запускать.
5. На 401, конечной ошибке, смене заявки/процесса, BACK или unmount завершить цикл. Устаревший ответ игнорировать.

D-03: использовать последовательное планирование после завершения запроса, без перекрывающихся `setInterval`-запросов. Это техническое уточнение интервала, а не новый серверный протокол. Максимальная длительность ожидания task исходником не задана; не изобретать бизнес-таймаут без Q-13.

REST.01 принимает видимый HTTP 303 через `validateStatus` в `state`. Для передачи `task` в теле 303 бэкенд должен вернуть JSON без `Location`. Если бэкенд возвращает `Location`, целевой ответ должен сам передавать валидный `{task}` (например, с HTTP 200).

## Требования к расширению транспорта

- Передавать `AbortSignal` активной операции в Axios для каждого из четырёх запросов. Сценарий отменяет устаревшие запросы и отдельно от таймаута обрабатывает отмену. Timeout задавать через параметры запроса после согласования Q-13.
- Передавать сценарию видимые `status` и `headers` для HTTP-ответов, включая `AxiosError.response`. Для видимого 303 сценарий разбирает тело как ответ с `task`. Сохранить JSON и multipart в исходящих запросах.
- Успешный `getDocument` возвращает `DocumentData`. Если сценарию нужны успешные status/headers, предоставить их вместе с уже разобранным документом, сохранив существующий интерфейс для текущих вызовов. Сетевые ошибки и ошибки разбора multipart должны оставаться различимыми.

## Проверка AC-22

13.11.2026 проверено в headless Chrome 157.0.8103.51 с локальным HTTP-бэкендом и синтетической заявкой. Тест загружает реальные `state`, `parseProcessResult` и `pollStatus` из приложения.

- При 303 без `Location` Axios с настройками по умолчанию предоставил статус и тело в `AxiosError.response`. После изменения `state` вернул тот же 303 и `{task}` как успешный результат. Тестовая страница разобрала его и передала тот же task в POST `/poll/status`, который вернул 200 с очередным task.
- При 303 с `Location` Chrome отправил GET на целевой маршрут. Axios получил конечный HTTP 200 и его тело. Исходный task из тела 303 браузерному коду недоступен.

Запуск из корня проекта с доступом к loopback:

```powershell
node docs/signing/check-browser-303.mjs 'C:/Program Files/Google/Chrome/Application/chrome.exe'
```

В задаче 09 повторить проверку на интеграционном бэкенде. В DevTools Network зафиксировать цепочку методов и статусов, наличие `Location`, результат Axios и переход к polling на синтетической заявке.
