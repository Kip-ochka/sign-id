# КриптоПро: операции и ограничения

Основание: R-03, R-11–R-21. Существующий код — пример. Реальную криптографическую совместимость подтверждают тестовые сертификаты, плагин и бэкенд, не TypeScript-типы.

## Целевой минимальный набор

1. Проверить расширение/Browser Plug-in и инициализацию cades API.
2. Проверить CSP и согласованную версию/конфигурацию.
3. Получить сертификаты, извлечь реквизиты, применить фильтры.
4. Для выбранного сертификата получить алгоритм, нужные сведения о TSP и публичный сертификат Base64.
5. Создать подпись с согласованными параметрами.
6. Вернуть результат или ошибку с исходным кодом, стадией и причиной для сопоставления со справочником.

Адаптер не открывает STATUS, не делает `getSettings`, не хранит React state, не регистрирует новый сертификат и не устанавливает CSP. Экспорт закрытого ключа не требуется.

## Маппинг реквизитов из исходника

| Поле DTO/фильтра   | Область сертификата | OID               | Friendly |
| ------------------ | ------------------- | ----------------- | -------- |
| person.last_name   | Subject             | 2.5.4.4           | SN       |
| person.first_name  | Subject             | 2.5.4.42          | G        |
| person.middle_name | Subject             | 2.5.4.43          | I        |
| person.inn         | Subject             | 1.2.643.3.131.1.1 | INN      |
| person.snils       | Subject             | 1.2.643.100.3     | SNILS    |
| organization.name  | Subject             | 2.5.4.10          | O        |
| organization.inn   | Subject             | 1.2.643.100.4     | INNLE    |
| organization.ogrn  | Subject             | 1.2.643.100.1     | OGRN     |
| issuer.name        | Issuer              | 2.5.4.10          | O        |
| issuer.inn         | Issuer              | 1.2.643.100.4     | INNLE    |
| issuer.ogrn        | Issuer              | 1.2.643.100.1     | OGRN     |

Subject и Issuer читаются раздельно. Значение `G` целиком записывается в `person.first_name`, в том числе если содержит имя и отчество. `person.middle_name` читается из `I`, при его отсутствии в REST передаётся пустая строка по Q-14. Изменение контракта для раздельных полей будет согласовано отдельно.

Все уровни `filters` необязательны. Каждое переданное поле содержит одну строку, и все переданные условия проверяются через AND. Отсутствующий реквизит сертификата не совпадает с заданным фильтром. При сравнении СНИЛС убираются пробелы и дефисы, для ИНН и ОГРН убираются пробелы с сохранением ведущих нулей. Текст сравнивается после Unicode NFC, выравнивания пробелов и приведения к нижнему регистру. В DTO сохраняются исходные значения. Поиск использует действующие сертификаты личного хранилища с привязкой к закрытому ключу, которую проверяет `getUserCertificates(true)`.

## Алгоритм и выбор хэша

| OID из требований | Алгоритм      | Константа CryptoPro                           | Хэш             |
| ----------------- | ------------- | --------------------------------------------- | --------------- |
| 1.2.643.7.1.1.3.2 | ГОСТ 2012-256 | CADESCOM_HASH_ALGORITHM_CP_GOST_3411_2012_256 | hash256         |
| 1.2.643.7.1.1.3.3 | ГОСТ 2012-512 | CADESCOM_HASH_ALGORITHM_CP_GOST_3411_2012_512 | hash512         |
| 1.2.643.2.2.3     | ГОСТ 2001     | CADESCOM_HASH_ALGORITHM_CP_GOST_3411          | Не используется |

По Q-09 адаптер определяет хэш по OID открытого ключа из `getAlgorithm()`. Для ГОСТ 2012-256 используется `1.2.643.7.1.1.1.1`, для ГОСТ 2012-512 — `1.2.643.7.1.1.1.2`. Таблица выше приводит OID алгоритмов подписи из исходных требований.

Полученный hex-хэш передавать в API подписи хэша в его ожидаемом формате; не хэшировать текст хэша заново и не считать hex строкой Base64. Источник для CHECK: `screen.test_document`; для документного SIGNING: элемент `screen.lists.documents`.

## Режимы MVP

При `single/other/detached` CHECK создаёт одну отсоединённую PKCS#7-подпись для `screen.test_document`. В SIGNING сценарий вызывает ту же операцию адаптера последовательно для каждого элемента `screen.lists.documents`. Сертификат один на весь список, хэш и формат берутся из текущего документа. После N успешных вызовов получается N подписей. Ошибка останавливает цикл и исключает частичную отправку.

При любом другом значении, включая `batch`, `archived`, `xml` и `attached`, показать локальный STATUS/WARNING по R-27. До перехода в fallback не вызывать операцию подписи, запрос справочника или отправку `check`/`signing`. Не требовать архивные хэши для валидного single. Остальные режимы отложены на следующие версии.

Для CHECK и SIGNING в MVP подтверждён профиль `CADESCOM_PKCS7_TYPE`. Клиент формирует базовую подпись без штампа времени. Бэкенд по-прежнему возвращает обязательный непустой `cryptopro.tsp_address`. Для операции со штампом времени действует согласованный приоритет: адрес из выбранного сертификата, если он однозначно распознаётся, иначе адрес из ответа. Такой операции в MVP нет. [Типы CryptoPro](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_enum/cadescom_cades_type), [CPSigner](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_class/cpsigner).

Через Browser Plug-in можно прочитать расширения выбранного `CPCertificate` или экспортировать его публичные данные через `Export` в Base64 и разобрать X.509 локально. В RFC 3161, приложение D, адрес описан в SIA (`1.3.6.1.5.5.7.1.11`) сертификата самой TSA как URI записи с методом `id-ad-timeStamping` (`1.3.6.1.5.5.7.48.3`). Наличие такой записи в сертификате подписанта зависит от профиля выпуска. Разбор следует привязать к расширению и методу доступа, подтверждённым на сертификате подписанта. На форуме CryptoPro приведён случай, когда TSP URL ошибочно поместили в AIA под методом `caIssuers`, предназначенным для получения сертификата УЦ. [CPCertificate](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_class/cpcertificate), [RFC 3161, приложение D](https://www.rfc-editor.org/rfc/rfc3161.html#appendix-D), [разбор сертификата на форуме](https://cryptopro.ru/forum2/default.aspx?find=unread&g=posts&t=15893).

В SIGNING `signHashes` заново находит выбранный сертификат по актуальным фильтрам, определяет OID открытого ключа и проверяет хэши всех документов для этого алгоритма до первого `SignHash`. Один экземпляр сертификата используется во всех вызовах. Адаптер один раз экспортирует публичный сертификат, проверяет Base64 каждой подписи и останавливается при отказе, в том числе при потере доступа к токену. CHECK вызывает ту же операцию для одного хэша через `signHash`. Синтетические тесты проверяют обе разрядности ГОСТ 2012 и передачу профиля PKCS#7 без обращения к TSA.

## Библиотека

В проекте уже объявлена `crypto-pro-actual-cades-plugin`. [Репозиторий библиотеки](https://github.com/Humble-saaber/crypto-pro-actual-cades-plugin) описывает API сертификатов, подписи и `execute`. Локальные объявления `lib/api/createDetachedSignature.d.ts` принимают `messageHash` и `options.hashedAlgorithm`; `createXMLSignature.d.ts` ожидает XML-содержимое. У detached-обёртки в просмотренных типах нет настройки TSP. Поэтому выбор высокоуровневого метода или `execute` должен опираться на требуемые параметры и проверку установленной версии.

Не копировать импорт `crypto-pro` из примеров README вместо уже выбранного пакета. Проверить, какую версию фиксирует lock-файл в момент реализации; не обновлять её автоматически.

## Кэш и повторная проверка

Кэш SETTING подтверждает прошлую настройку рабочего места, а не неизменность сертификата или доступность токена сейчас. CHECK и SIGNING заново ищут сертификаты. Сохранённый в памяти выбор — thumbprint/DTO, не долгоживущий COM-объект. Перед подписью выбранный сертификат должен оставаться доступным и подходить актуальным фильтрам.

Адаптер возвращает все совпадения с уникальным thumbprint. Для поиска и повторного отбора перед подписью он проверяет интервал `validFrom <= текущее время <= validTo`. Отсутствующая или неразбираемая дата исключает сертификат из выборки.

Не сохранять сертификаты, подписи и персональные реквизиты в `digital_id_sign`: исходник требует только идентификатор заявки, время и устройство. Ошибки localStorage не превращать в ложный успех.

Задача 05 реализует формат `{ version: 1, inquiry_id, device, checked_at }` с целым временем Unix в миллисекундах и строкой `navigator.userAgent` в поле `device` по Q-05. Проверка принимает совпадающую заявку и строку userAgent при неотрицательном возрасте меньше 24 часов. Устаревшие, повреждённые записи и записи неизвестной версии игнорируются. Следующая успешная настройка перезаписывает запись. Пропуск по кэшу не продлевает срок действия записи.

## Очистка примера

Сначала составить карту импортов/использования, затем заменить нужные операции и удалить неподключённое: генерацию запросов на сертификат, установку сертификатов, локальные копии cades_api, контейнерные утилиты, старые UI-компоненты/LESS и неиспользуемые экспорты. Сохранить только реально нужные части с тестом поведения. Проверить динамические обращения и глобальные побочные эффекты, а не только статические импорты.

Не очищать чужой незавершённый код без проверки текущего состояния рабочей копии. В этой аналитической поставке ничего из перечисленного не удаляется.

## Реализация задачи 04

Операции в `src/shared/services/cryptoPro/` используют зафиксированную в lock-файле версию 2.4.1.

| Операция                                                              | Вход и результат                                                                                                                                                        |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workplace.checkBrowserPlugin()`                                      | Лениво загружает пакет, проверяет доступность `CAdESCOM.About`. Сигнал callback уточняет стадию сбоя.                                                                   |
| `workplace.readCspVersion()`                                          | После проверки плагина получает `{ major, minor, build }` из `About.CSPVersion()` для применения согласованной политики Q-05.                                           |
| `adapter.findCertificates(filters?)`                                  | Заново запрашивает список, возвращает реквизиты, отпечаток, серийный номер и срок действия. Пустой результат отображается кодом `NO_CERT`.                              |
| `adapter.signHash({ thumbprint, mode, filters, hashes, parameters })` | Для `single/other/detached` заново находит сертификат, проверяет актуальные фильтры, экспортирует публичный сертификат и возвращает `{ signatureBase64, certificate }`. |

- `CryptoProError` сохраняет стадию, исходную причину и доступный код. Поле `code` принимает исходный код либо локальный код операции. Библиотека может заменить нативное сообщение при инициализации и в высокоуровневых операциях. Сценарные обработчики передают `code` существующему resolver из `src/process/network.ts`.
- `getAlgorithm()` читает OID открытого ключа. `1.2.643.7.1.1.1.1` выбирает `hash256`, `1.2.643.7.1.1.1.2` — `hash512`. ГОСТ 2001 и прочие OID отклоняются. В `SetHashValue` передаётся готовый hex, затем выполняется один `SignHash` с тем же сертификатом, который прошёл фильтр. [CryptoPro PublicKey](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_class/publickey), [пример SignHash](https://docs.cryptopro.ru/cades/plugin/plugin-samples/plugin-samples-cades-sign-hash), [RFC 9215 §4](https://www.rfc-editor.org/rfc/rfc9215.html#section-4).
- `execute` позволяет указать профиль и использовать уже выбранный COM-сертификат. В MVP вызывающий код задаёт `{ profile: 'PKCS7' }`. Передача TSA предусмотрена в адаптере для явно выбранного профиля CAdES-T или CAdES-X Long Type 1.
- Маппинг Subject/Issuer применяет OID и указанные в таблице псевдонимы. Парсер DN принимает локализованные имена атрибутов, в том числе составные, как `ИНН организации`. Незнакомое имя пропускается при сопоставлении полей. Значения в кавычках, удвоенные кавычки, экранированные разделители и hex-экранирование разбираются до нормализации для сравнения D-04. Различающиеся значения одного атрибута считаются неоднозначными. Для фильтрации и списка отсутствующие реквизиты остаются optional. В результате `signHash`, подготовленном для REST, каждый отсутствующий или неоднозначный реквизит из `person`, `organization` и `issuer` заполняется пустой строкой по Q-14.
- Проверка Base64 допускает переносы строк плагина и проверяет каноническую кодировку результата. AC-13 проверяет выбор хэша, алгоритма и профиля на синтетических данных. Приём реальной подписи бэкендом находится за пределами приёмки проекта.
