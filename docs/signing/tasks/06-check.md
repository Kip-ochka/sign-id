# 06. Тестовая подпись и подтверждение сертификата

Статус: не начата. Зависимость: 05. Результат — CHECK от получения ответа до передачи тестовой подписи бэкенду.

## Вход

R-14–R-17, [API](../API_CONTRACT.md), [CryptoPro](../CRYPTO_CONTRACT.md), [UI](../UI_SPEC.md). Для настоящего подписания обязательны решения Q-09/Q-12/Q-14/Q-15. Объём MVP определён в R-20.

## Работа

1. При каждом новом CHECK получить актуальные сертификаты с фильтрами ответа через адаптер. Успешный SETTING и кэш не заменяют эту проверку.
2. 0 → STATUS NO_CERT; 1 → использовать автоматически; несколько → выбор с ФИО и организацией, без доступной кнопки до выбора. Не сохранять выбор сертификата, который не входит в новую выборку.
3. Показать согласие и ссылку из screen; основное действие по кнопке. Просмотр экрана и выбор сертификата не запускают подпись.
4. До подписи проверить test_document, сертификат и нужный хэш. При параметрах вне `single/other/detached` сразу показать локальный fallback по R-27. CryptoPro не подписывает, `getSettings` и `state('check')` не вызываются.
5. Выполнить подпись через адаптер. Разделить стадии «создание подписи» и «отправка». Для разрешённых по Q-12 повторов отправки использовать готовую подпись и бюджет `max(1, retry_count)` вместе с первой отправкой.
6. Составить DTO из исходного test_document и данных подписавшего сертификата. Передать state('check') с request/test.sig/сертификатом по существующему multipart-контракту.
7. Ответ передать общему диспетчеру; не предполагать, что это обязательно SIGNING. Ошибки CryptoPro обрабатывать через справочник, ошибки HTTP — через общий сценарий. При невалидном ответе RESPONSE_ERROR.
8. Смена заявки/BACK/unmount инвалидирует результат; повторный клик во время подписи или отправки не создаёт новый вызов. BACK после ошибки не подписывает автоматически.

## Не входит

Основные документы и их просмотр, скрытая смена сертификата вместо выбранного, фиктивное согласие или серверная проверка подписи на фронтенде.

## Приёмка

AC-10–AC-14, AC-18, AC-24/AC-26. Проверить число вызовов адаптера, правильный hash/алгоритм/TSP, подпись по явному действию, реквизиты из сертификата вместо filters, отсутствие бинарных полей в JSON, test.sig и MIME, общее поведение process/task.

Нужны сценарии ошибки подписи, исчезнувшего сертификата, HTTP retry готового результата и восстановления после STATUS. При реальном окружении подтвердить принятие тестовой подписи бэкендом; иначе отметить интеграцию непроверенной.
