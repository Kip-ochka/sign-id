# Задание для ИИ-агента по рефакторингу API-слоя SIGNING

Выполни рефакторинг `src/shared/api`, сохранив HTTP-контракт и публичный интерфейс модуля. Цель — упростить типизацию и сделать код запросов и обработки ответов понятным по месту использования. Вноси изменения небольшими шагами и проверяй их на локальных синтетических данных.

## Область работы

- `src/shared/api/index.ts` — публичные экспорты. Сохрани имена, пути импорта и формы результатов. `getSettings`, `pollStatus` и `state` возвращают `AxiosResponse`, `getDocument` возвращает `DocumentData`.
- `src/shared/api/http-client.ts` и `requests.ts` — Axios-клиент, маршруты и сериализация запросов. Сохрани работу путей `/proxy/...` через хостинг, текущее отсутствие `baseURL` и интерцепторов.
- `src/shared/api/schemas/` и `types.ts` — Zod-схемы и типы контракта. Выводи типы из схем там, где они описывают одну и ту же форму данных. Сохрани используемые имена типов и схем.
- `src/shared/api/helpers/` — создание multipart-частей и разбор ответа с документом. Используй существующие функции там, где они уже описывают нужное преобразование.

`src/App.tsx` пока содержит демонстрационный счётчик и не подключён к API. Ограничь изменения API-слоем. Для проверок используй существующие TypeScript, Axios и браузерные API. Сохрани зависимости, конфигурацию, UI и интеграцию CryptoPro в текущем виде.

## HTTP-контракт

| Операция                | Запрос                                                                                                    | Результат                                                                                                        |
| ----------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `getSettings(key)`      | `GET /proxy/services/sbercraft-dict-ext/serviceProperties/corp-digital-id-sign/{key}`                     | Для литерала `settings` — `AxiosResponse<SettingsResponse>`. Для ключа экрана — `AxiosResponse<ScreenResponse>`. |
| `getDocument(body)`     | `POST /proxy/services/corp-digital-id-sign/api/public/v1/document` с JSON и `responseType: 'arraybuffer'` | `DocumentData` из частей `response` и `file` ответа `multipart/mixed`.                                           |
| `pollStatus(body)`      | `POST /proxy/services/corp-digital-id-sign/api/public/v1/poll/status` с JSON                              | `AxiosResponse` с `{ task }` или процессом.                                                                      |
| `state(event, body, …)` | `POST /proxy/services/corp-digital-id-sign/api/public/v1/state/{event}`                                   | `AxiosResponse` с `{ task }` или процессом. Форма ответа общая для всех событий.                                 |

- Для `state('start', …)` и `state('ready', …)` отправляй JSON. Для `check` и `signing` третий аргумент с файлами обязателен. Отправляй `FormData` в порядке `request`, `signatures`, `certificates`. `request` — JSON-часть с типом `application/json`. Каждая подпись и каждый сертификат занимают отдельную часть под своим повторяющимся именем. Передавай `FormData` клиенту, чтобы он сформировал `boundary`.
- Подпись передавай как декодированные из Base64 байты с MIME-типом `application/pkcs7-signature`. Сохрани имена `test.sig` для `check` и `<document.id>.sig` для `signing`. Сертификат передавай как текст Base64 в `<serial_number>.b64` с типом `text/plain`. В JSON-части подписи отсутствуют, а у объектов сертификатов передаются метаданные без `certificate_base64`. При проверке формы запроса учитывай, что TypeScript и Axios сами лишние поля из объекта не удаляют.
- Для `getDocument` сохрани извлечение `boundary` из заголовка `Content-Type`, чтение JSON из `response`, проверку метаданных через Zod и чтение `file` как текста Base64. Сохрани поддержку частей, представленных строкой или `File`. В текущем коде схема всего `DocumentData` не применяется к результату парсера. Добавление проверки Base64 меняет множество принимаемых ответов.
- `state` и `pollStatus` могут вернуть процессы `SETTING`, `CHECK`, `SIGNING`, `STATUS` или `{ task }`. Комментарии связывают `303` с отложенной обработкой, но текущий клиент использует стандартное поведение Axios. Отдельно установи, что видит вызывающий код при `303` в браузере. Проверка через подставной адаптер не подтверждает поведение реального редиректа. Сохрани текущие настройки обработки статусов и редиректов. Если прокси недоступен, зафиксируй это в отчёте.

## Порядок работы

1. Прочитай публичные экспорты, реализации запросов, Zod-схемы и файловые утилиты. Найди вызовы и прямые импорты в проекте. Запусти исходные `typecheck`, `lint` и `format:check`. Для спорных частей контракта сначала используй доступные спецификации и примеры. `PLAN.md` упомянут в комментарии, но в текущей рабочей копии отсутствует.
2. Упрости связь между схемами запросов `state`, событием, телом и обязательностью файлов. Проверь вывод типов для литеральных событий и переменной типа `StateEvent`. Рассмотри прямой индексированный доступ к карте схем и дискриминированное объединение кортежей, если они позволяют убрать `as StateFiles` и лишние приведения с сохранением совместимости. Проверь, что тело `check` и тело `signing` нельзя перепутать.
3. Проверь типизацию `getSettings`. `ScreenKey = Exclude<string, 'settings'>` по-прежнему равен `string`, поэтому по произвольному ключу TypeScript не может гарантировать форму ответа. Сохрани действующую перегрузку для литерала `settings` и опиши ограничение для динамических ключей. Изменение публичного типа для динамического ключа требует отдельного согласования.
4. Сократи подтверждённое дублирование в схемах, типах и обработчиках. Сохрани различия между DTO, файловыми аргументами и разобранным документом. Сравни типы и поведение до и после изменений. Новую обязательную Zod-валидацию JSON-запросов или ответов, изменения в сериализации, ретраи и изменение обработки `303` вынеси в отдельные предложения, если они нужны.

## Проверка результата

Запусти `npm run typecheck`, `npm run lint`, `npm run format:check` и `npm run build`. В проекте нет `npm test`. Используй локальные проверки с синтетическими телами запросов и ответов, без отправки данных на рабочий сервис.

- **Типы.** Проверь корректные вызовы всех четырёх событий `state` и ошибки типов при отсутствии файлов для `check`/`signing`, передаче файлов для `start`/`ready` и несовпадении тела с событием. Проверь формы результата `getSettings('settings')`, `getSettings` с ключом экрана и `getDocument`.
- **Запросы.** Перехвати вызовы Axios и сравни HTTP-метод, URL, JSON и `responseType`. Для `check` и `signing` проверь порядок и имена частей, MIME-типы, имена файлов, бинарное содержимое подписи и текст сертификата. Проверь JSON-часть отдельно от файлов.
- **Ответы.** Проверь корректный `multipart/mixed` с `boundary` в кавычках и без кавычек, неверный `Content-Type`, отсутствие одной из частей, битый JSON и метаданные, отклоняемые Zod. Проверь, что `{ task }` и ответы с `process` по-прежнему доступны вызывающему коду в `response.data`.

В итоговом отчёте укажи изменённые файлы, что упростилось, какие проверки выполнены и что осталось непроверенным. Перечисли отдельно любые обнаруженные расхождения между комментариями, типами и фактическим поведением.
