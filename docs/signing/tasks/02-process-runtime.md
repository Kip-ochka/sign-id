# 02. Состояние процесса, START, сеть и ошибки

Статус: завершена на уровне сценарной логики. Зависимость: подтверждённые модели задачи 01. Результат — единый управляющий сценарий, доступный будущим экранам.

## Вход

[Требования](../REQUIREMENTS.md) R-04–R-08, R-22–R-28; [API](../API_CONTRACT.md), [решения](../DECISIONS.md), [UI](../UI_SPEC.md).

## Работа

1. Хранить состояние процесса в React Context через `useState` по D-01: inquiryId, settings, последний валидный ответ, серверный process отдельно от отображаемого экрана, task, request id и снимок возврата. Сохранять последнее валидное `SETTING.session` в localStorage на 115 минут и `SIGNING.token` только в памяти Context, в том числе при SETTING cache hit. Восстанавливать действующую сессию при загрузке и удалять истёкшую; передавать token в `X-integrity-token` только для document/signing. Новое значение заменяет прежнее. Для `Session-id` применять правила Q-02.
2. START: единственный непустой query `id` → settings/defaults → start → валидация → диспетчер. При пропущенном, пустом, пробельном или повторном id показать локальный STATUS «Ссылка недействительна» / «Откройте ссылку из SMS» без запросов и кнопки повтора. Убрать fallback и запись `digitalid_sign_inq`. Перерисовка не запускает START повторно.
3. Диспетчер принимает любой поддержанный process/task. Для SETTING предусмотреть асинхронную проверку кэша **перед сменой экрана**, подключаемую в задаче 05. Не создавать краткое мигание SETTING.
4. Централизовать HTTP-матрицу. `retry_count=3` даёт максимум три вызова на операцию вместе с первым, 0 и 1 дают один. Новый обычный poll получает новый бюджет. При `retry_addition=0` использовать только `retry_time`. Timeout — Q-13, повторы отправки подписи — Q-12.
5. Реализовать polling с первой задержкой, сменой task, отсутствием параллельных запросов и остановкой на process/error/401/уходе. Отделить poll-интервал от retry-задержки.
6. Первый 401 от REST.01/02/03 очищает старую сессию и активные операции и вызывает START один раз. Второй 401 до новой заявки или явного повтора переводит в STATUS `RESPONSE_ERROR`. Успешный ответ рестарта сам по себе лимит не сбрасывает.
7. Общий error resolver: code/stage → справочник или fallback. Учесть signingErrorOverrides, null, неуспех getSettings и приоритет новых правил над INTERMEDIATE_ERROR старого справочника.
8. BACK: восстановление последнего рабочего экрана без автоподписи; fallback на START при отсутствии истории. Дать UI команды повторного действия, а не исполняемый серверный код `action`.
9. Сохранять X-Request-Id исходной операции; выдавать UI модель STATUS. ErrorBoundary отображает локальный fallback и имеет управляемое восстановление. Асинхронные ошибки обрабатывать явно: ErrorBoundary не заменяет catch сетевых/криптографических операций.
10. Отмена/идентификатор запуска: поздние ответы, таймеры и завершение плагина после смены заявки игнорируются. Не считать невозможность отменить плагин поводом применить старый результат.

11. Только в STATUS/SUCCESS запускать `timer` в миллисекундах с момента показа, если у `accent` есть распознанное действие. Таймер и клик используют один обработчик. Первый запуск действия исключает повтор. Ручное действие, смена экрана/заявки и unmount отменяют таймер. Проверить AC-23, включая отсутствие таймера, WARNING и ERROR и гонку с кликом.

## Не входит

Финальный UI, реальные проверки CSP/сертификатов и подпись. Для них использовать тестовые адаптеры с явным статусом разработки.

## Приёмка

AC-02–AC-06, AC-20/AC-21, AC-23–AC-26 на уровне сценарной логики. Проверить fake timers, счётчики вызовов, обновлённый task id, ошибку каждого типа, успешный retry и исчерпание. BACK после STATUS не возвращает снова STATUS. Известная ошибка getSettings не запускает цепочку новых getSettings.

Typecheck и целевые Jest-тесты проходят. Решения по 303/401/timeout документированы; доступность тестового сценария HTTP 303 зафиксирована.

## Передача

Описать команды/состояния для задачи 03, точку подключения кэша для 05 и адаптера для 04. Обновить PROGRESS и принятые Q-*.

## Где находится реализация

- [requests.ts](../../../src/process/requests.ts) — отдельные сетевые функции для start, ready, check, signing, poll и document, а также для настроек и экрана ошибки.
- [useProcess.ts](../../../src/process/useProcess.ts) — обработчики сценария и состояние заявки. Каждый обработчик вызывает свой сетевой запрос и применяет ответ.
- [polling.ts](../../../src/process/polling.ts) — пауза, запрос статуса и повтор при следующем task.
- [useStatusActions.ts](../../../src/process/useStatusActions.ts) — общее действие кнопки и таймера SUCCESS.

## Интерфейс для следующих задач

- `useSigningProcess()` возвращает `state` и `commands`. `state.serverProcess` и `state.lastResponse` отражают серверный ответ, в том числе при WAITING и после BACK. `state.busy` показывает активную команду. `state.requestId` и `state.errorKey` доступны на STATUS.
- `useSigningNavigation()` возвращает текущий экран `current`, предыдущий шаг `from`, назначение последнего валидного ответа `target` (для task это WAITING), рабочий шаг возврата `backTo` и команду `back()`. Если рабочего экрана ещё нет, `backTo` указывает на START. Монтировать `NavigationProvider` внутри `ProcessProvider` и выбирать экран по `current.process`.
- Для STATUS использовать `canActivate(button)` и `useStatusActions(screen, back)`. Хук возвращает действие для клика и ставит таймер на SUCCESS. `back()` восстанавливает рабочий экран, а при отсутствии истории запускает START. Ручной BACK сбрасывает бюджет автоматического рестарта после 401. Отдельной команды `retry` в Context нет. `App` получает `inquiryId` при запуске и монтирует `ProcessProvider` с `key={inquiryId}`. Начальное значение читает `main.tsx` из SMS-ссылки.
- Задача 05 подключает `hasSettingCache(inquiryId, response, signal)` к `ProcessProvider`. При попадании обработчик ответа отправляет ready до показа SETTING. После ручной проверки будущий экран вызывает `ready()`.
- Экраны CHECK и SIGNING используют `submitCheck(thumbprint)` и `submitSigning(thumbprint)`. Подготовка подписи и общий `submitSignature(prepare)` остаются внутренней реализацией `useProcess`; ошибки адаптера обрабатываются в соответствующем сценарии. Задача 07 использует `downloadDocument(documentId)` и проверяет данные для просмотра или скачивания. Тестовые данные, отложенные ответы и ошибки задаются моками в тестах, без вспомогательных команд в Context.
