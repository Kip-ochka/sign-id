# 03. Накидать и реализовать простой интерфейс

Статус: завершена в границах UI. Зависимость от модели задачи 02 закрыта. Реальная проверка, операции подписи и скачивание относятся к задачам 04–08.

## Вход

[UI_SPEC.md](../UI_SPEC.md), R-02/R-11/R-15/R-16/R-18/R-24/R-25/R-28 из [требований](../REQUIREMENTS.md), фикстуры задачи 01.

## Работа

1. На основе текстовой накидки подготовить простые макеты START, SETTING, CHECK, SIGNING, WAITING и трёх вариантов STATUS. Включить загрузку, ошибку этапа, 0/1/несколько сертификатов, длинные списки и необязательные поля.
2. Выбрать нейтральную сетку, типографику, состояния кнопок и способ просмотра документа. Сохранить краткое объяснение в UI_SPEC; готового брендового дизайна не ожидать.
3. Собрать общий каркас и переиспользуемые элементы: кнопки, статус, список проверки, выбор сертификата, список документов, индикатор ожидания, ссылка согласия. Не создавать универсальный серверный HTML-renderer.
4. Оформить через `.module.css`. Общие токены/reset допустимы в одном глобальном файле. Не подключать Router, LESS из примера или новый UI-kit без обоснования.
5. Выбирать экран по `current.process` из `useSigningNavigation()`. BACK восстанавливает экран из состояния заявки. Для полного внешнего URL в STATUS использовать действие по Q-11.
6. Выводить тексты из screen; локальные тексты допустимы для START/WAITING/fallback. Не зашивать в UI ФИО, примерные названия документов и «Шаг 1 из 4».
   Для недействительной ссылки показать локальный STATUS «Ссылка недействительна» с текстом «Откройте ссылку из SMS». В этом состоянии зона действий отсутствует.
7. Подключить состояния disabled/loading, error detail, request id и ErrorBoundary. Серверные значения `action` не исполнять произвольно. Подключить кнопки через `useStatusActions()`. Клик и таймер SUCCESS используют один обработчик. Ручное действие любой кнопки отменяет отсчёт. Не добавлять второй таймер в компонент.
8. Подготовить воспроизводимый просмотр фикстур для разработки; демонстрационные переходы не должны попасть в пользовательскую навигацию.

## Не входит

Работа с реальным плагином, подпись и настоящая загрузка файлов. Компоненты пока используют команды/контракты следующих задач; фиктивный успех не должен показываться как реальная подпись.

## Приёмка

AC-01, AC-11/AC-12, AC-15, AC-23/AC-25/AC-27 на уровне UI. Вручную проверить 360/768/1280 px, клавиатуру, focus, чтение ошибок и длинные строки. Сохранить скриншоты состояний и указать их в отчёте.

Не требуется сначала писать тесты, повторяющие JSX. Нужны проверяемые сценарии выбора/блокировки/возврата; при автоматизации учесть, что Jest сейчас Node и без TSX/DOM-настройки. Выполнить typecheck, lint и build.

## Передача

Обновить UI_SPEC и PROGRESS: выбранный способ просмотра, компоненты/команды, где ещё стоят тестовые данные. Функциональность не считать готовой до подключения последующих задач.
