# Решения и вопросы

Ниже отделены прямые ограничения пользователя, предложения аналитика и недостающие сведения. Никакой вопрос не считается решённым из-за отсутствия ответа. Разрешено продолжать независимую работу, не обозначая заблокированные сценарии реализованными.

## Зафиксированные ограничения

- Реализация выполняется по отдельному запросу на конкретную задачу.
- Навигация по состоянию, без React Router; CSS Modules.
- Приложение читает `id` из SMS-ссылки один раз при загрузке. Выбор экрана и BACK используют состояние текущей заявки. Полный URL в кнопке STATUS относится к внешнему переходу по Q-11.
- Простые экраны нужно спроектировать и реализовать отдельной задачей.
- Криптослой примера требуется очистить, оставив реально используемое.
- `inquiry_id` из ссылки и в кэше — не session.
- Неизвестные ошибки и ErrorBoundary используют локальный fallback без getSettings.

## Клиентские решения от 13.11.2026

- **Q-01.** `retry_count` ограничивает число HTTP-вызовов одной операции с учётом первого. При 3 максимум три вызова, при 0 и 1 один. Следующий обычный poll и новый явный запуск после BACK получают новый бюджет. Перерисовка и retry бюджет не сбрасывают. При `retry_addition=0` пауза равна `retry_time`. Исходник повторяет «Всего retry_count попыток». Область бюджета и значения нулей выбраны аналитиком. Задачи 01, 02, 06–09.
- **Q-03.** Заявка определяется единственным непустым query `id`. Отсутствующий, пустой, пробельный или повторный параметр даёт локальный STATUS «Ссылка недействительна» / «Откройте ссылку из SMS» без запросов и кнопки повтора. Валидный id используется после URL-декодирования без дополнительной нормализации. Убрать чтение и запись `digitalid_sign_inq`. Клиентское решение аналитика на основании сценария входа по ссылке. Задачи 01–03, 05, 09.
- **Q-04, клиентская часть.** Валидный `{task}` от REST.01 при HTTP 200 или доступном 303 запускает polling. Поддержка 200 следует из описания START. После первого 401 перезапустить START без старой сессии. Второй 401 до новой заявки или явного повтора пользователя даёт STATUS `RESPONSE_ERROR`, даже если рестарт успел вернуть успешный ответ. Лимит выбран аналитиком. Видимый 303 принимается REST.01. Поведение браузера проверено с локальным HTTP-бэкендом. Задачи 01, 02, 07, 09.

## Временное поведение в задаче 02

- **Q-11.** По уточнению пользователя поле `url` в кнопке STATUS содержит полный адрес следующего процесса, например `https://some-cite.com/any`. Обработчик кнопок STATUS проверяет абсолютный HTTP(S)-адрес и передаёт его браузеру. Если в кнопке заданы одновременно URL и process, действие недоступно до уточнения семантики.
- **Q-12.** REST.01 для check/signing повторяет отправку готовых файлов при явных HTTP 429/504 с прежними данными и `req_time`. Локальный таймаут отправки ведёт в `RESPONSE_ERROR` без автоматической повторной отправки до подтверждения идемпотентности.
- **Q-13.** Сетевой обработчик распознаёт таймаут Axios (`ECONNABORTED` / `ETIMEDOUT` без HTTP-ответа). Клиентский дедлайн запроса и общее ограничение ожидания task оставлены открытыми. Прочие статусы и сетевые ошибки завершают операцию по D-06.

## Решения пользователя по MVP от 13.11.2026

- **Q-02.** Сохранять `session` из валидного SETTING и `token` из валидного SIGNING в Context текущего запуска. Схемы API уже содержат оба поля. Сохранение переживает переходы между экранами, в том числе polling. Новое значение заменяет прежнее. START при 401 и смена заявки очищают оба поля. Сведения о способе передачи не предоставлены. В MVP запросы остаются в текущем формате. Задачи 01, 02, 09.
- **Q-06–Q-08.** MVP поддерживает `single/other/detached` с PKCS#7. По уточнению пользователя SIGNING последовательно подписывает каждый документ из списка одним выбранным сертификатом. Для каждого документа вызывается одна и та же операция с его хэшем. После получения всех N подписей отправить один `state('signing')` с N документами и N файлами `<document.id>.sig`. При ошибке любой подписи остановить цикл и обработать ошибку без частичной отправки. CHECK подписывает один тестовый документ. `batch`, `archived`, `xml`, `attached` и неизвестные значения дают локальный fallback R-27. Задачи 01, 04, 08, 09.
- **Q-10.** По истечении `STATUS.timer` выполнить действие основной кнопки `accent`. Значение задано в миллисекундах от показа экрана. Ноль запускает действие сразу после показа. Отсутствие поля оставляет экран до действия пользователя. Ручное действие любой кнопки, уход с экрана и смена заявки отменяют таймер. При отсутствии распознанного действия `accent` экран остаётся видимым. Клик и таймер используют общий обработчик с однократным выполнением. Уточнение от 14.11.2026 ограничивает таймер уровнем SUCCESS. На WARNING и ERROR требуются ручные действия. Задачи 02, 03, 09.

## Результаты сверки в задаче 01 от 13.11.2026

- **Уточнение пользователя.** `/proxy/services/...` — путь API бэкенда. Для AC-22 требуется сценарий с HTTP 303 на этом маршруте.

- **Q-01, Q-03, клиентская часть Q-04.** Бюджет попыток, разбор единственного `id` и выбор действия при первом и повторном 401 закреплены в моделях и тестах. Хранение счётчиков, запуск запросов и переходы подключаются в задаче 02. В Chrome подтверждено: 303 без Location передаёт тело task, с Location браузер выполняет GET и передаёт конечный ответ. Результат и проверка для задачи 09 приведены в [API_CONTRACT.md](API_CONTRACT.md#проверка-ac-22).
- **Q-02.** Локальные HTTP-тесты подтвердили сохранение `SETTING.session` и `SIGNING.token` при разборе обоих типов запросов. Управление значениями в Context остаётся задачей 02.
- **D-06.** Модель отклоняет пустой и пробельный `task`, а также тело с обоими дискриминантами. Это временная клиентская политика. Сетевая часть D-06 и Q-13 остаётся открытой.
- **Q-06–Q-08, Q-14.** Схема принимает `single/other/detached` без архивных хэшей. Для CHECK и SIGNING распознаваемый неподдерживаемый режим даёт локальный fallback до проверки полей экрана и подписи. Открыты обязательность криптографических полей для отложенных режимов и формат отсутствующих реквизитов сертификатов.
- **Q-10.** Модель STATUS сохраняет числовой `timer`, включая ноль. Выполнение действия `accent` остаётся задачами 02 и 03.

## Результаты сверки в задаче 04 от 14.11.2026

- **Q-05.** Адаптер получает major/minor/build отдельно от проверки плагина. Список допустимых сборок и способ определения устройства остаются у владельца процесса/CryptoPro-интеграции.
- **Q-09.** В установленной версии 2.4.1 `getAlgorithm()` читает `PublicKey().Algorithm.Value`. Маппинг OID открытого ключа для ГОСТ 2012-256/512 сверили с [документацией CryptoPro](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_class/publickey) и [RFC 9215 §4](https://www.rfc-editor.org/rfc/rfc9215.html#section-4). Профиль и адрес TSA передаются явно. Бэкенд и CryptoPro-интеграция должны подтвердить политику выбора профиля, источник адреса в сертификате, допустимые адреса и поведение при отсутствии адреса.
- **Q-14, Q-15.** Адаптер возвращает отсутствующие и неоднозначные поля как отсутствующие. До отправки требуется согласовать их представление в REST. Фильтрация использует рабочее предложение D-04. `getUserCertificates(true)` версии 2.4.1 читает текущее личное хранилище, проверяет срок действия и наличие свойства провайдера закрытого ключа. Критерии доверия, доступности контейнера и квалифицированности на реальных сертификатах остаются открытыми.

### Уточнение по адресу TSP

- **Подтверждено пользователем.** Сертификаты подписантов могут выпускать разные УЦ. Правило извлечения должно быть общим для всех УЦ.
- **Подтверждено пользователем.** Бэкенд всегда возвращает непустой `cryptopro.tsp_address`. Исходный приоритет для CHECK и SIGNING сохраняется: адрес из выбранного сертификата при наличии, иначе адрес бэкенда. Целевое окружение использует КриптоПро CSP 5.0 и выше.
- **Q-09, результаты поиска.** RFC 3161, приложение D, описывает необязательный адрес в SIA сертификата самой TSA. OID расширения SIA — `1.3.6.1.5.5.7.1.11`, OID метода доступа внутри него — `1.3.6.1.5.5.7.48.3`. Для сертификата подписанта Browser Plug-in документирует доступ к расширениям и явную передачу адреса в `CPSigner.TSAAddress`. Формат поля в сертификатах подписантов нашего процесса нужно подтвердить на образце или по спецификации выпускающего УЦ. Выбор профиля и требование штампа остаются открытыми. [RFC 3161, приложение D](https://www.rfc-editor.org/rfc/rfc3161.html#appendix-D), [RFC 5280 §4.2.2.2](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.2.2), [CPCertificate](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_class/cpcertificate), [CPSigner](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_class/cpsigner).

## Как фиксировать ответ

Для каждого Q-* записать: статус, точный ответ, источник/автор и дату, пример запроса/ответа или сертификата без персональных данных, затронутые задачи и AC-*. Затем обновить спецификацию и тестовый пример. Не оставлять принятое решение только в чате или отчёте агента.

Не все вопросы требуют участия пользователя прямо сейчас: задача этого этапа — качественная постановка. Перед интеграцией владелец реализации должен получить ответы у соответствующих владельцев контрактов; UI и независимые части не должны простаивать из-за одного заблокированного режима.
